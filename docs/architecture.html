How noiseman makes noise

A small background daemon owns the audio. The CLI, TUI and optional GUI control it by sending text lines over a Unix socket. The noise itself comes from one dependency-free Rust crate that also compiles to a 4 KB WebAssembly module for the browser demo.

The whole system

noiseman has two halves and one shared core. Frontends never import backend code: everything they know about the player arrives on the socket as state or err lines, or the one protocol reply. Both the daemon and the web demo generate samples from noiseman-core, so every noise kind sounds the same in both.

Inside the daemon

One player thread owns all playback state and handles messages one at a time from a single channel. Per-client socket readers parse incoming lines (answering syntax errors and the protocol request directly) and forward the other commands to that channel; the audio error callback logs every error and posts AudioLost to the same channel when the device or stream is gone. The audio callback never takes a lock: it reads the requested kind and gain from two atomics once per buffer and renders the buffer with its own Voice, choosing the noise generator once per buffer rather than per sample.

Playing, fading, muted

Muting does not cut the stream at once. The target gain drops to zero and fades along an S-curve to exactly 0 in 20 ms; the player allows one device buffer for the audio callback to pick up the new gain, three for audio already queued in the device and 20 ms of slack before dropping the stream. Once muted with no clients connected, the daemon is completely idle: two threads (main and accept) and zero wakeups.

The sound core

noiseman-core has no dependencies, does no I/O and never allocates. Noise turns a xorshift64 generator into five colours of noise, each scaled to about −18 dBFS RMS. gain(vol) maps volume 0–100 on a square law, and Voice smooths every gain and kind change with a fade that reaches its target in exactly 20 ms (960 samples at 48 kHz) along a smoothstep S-curve, 3t² − 2t³, which starts and ends with zero slope.

The protocol

One request per line, one reply per request. Every reply is either a state line or an err line, except the reply to protocol, which clients ask a daemon they did not start so they can warn when its protocol version (semver, separate from the app’s) is incompatible. After watch, the daemon also pushes a state line whenever anything changes; that is how the TUI and GUI stay in sync with each other and with the CLI.

# → request          ← reply
status               state brown 50 playing
kind pink            state pink 50 playing
vol +5               state pink 55 playing
mute                 state pink 55 muted
vol loud             err bad volume "loud"
protocol             protocol 0.1.0
watch                state pink 55 muted
                     state pink 55 playing   # pushed when another client unmutes

The other requests are vol N, vol -N, unmute, toggle and quit. An audio failure is appended to the state line as an error message, and the daemon reports itself muted.

In the browser

The web demo wraps noiseman-core in a raw WASM module with two exports (synth_init and synth_render) and no wasm-bindgen. The synth lives in static memory, so the module has no heap and stays near 4 KB. After setup, the page only sends the worklet two numbers: kind and vol.
